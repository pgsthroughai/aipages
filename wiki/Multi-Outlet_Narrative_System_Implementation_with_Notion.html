Overview

This guide documents the practical implementation of the Multi-Outlet Narrative System using Notion as the database platform and Claude as the AI assistant for content creation and management. The implementation demonstrates how to maintain strict epistemological boundaries between immutable facts (Events) and mutable interpretations (Briefs) while enabling multiple narrative perspectives to coexist and interact.

The reference implementation uses a Sherlock Holmes Victorian detective narrative with six distinct "outlets" (narrative voices) that observe and interpret the same factual events from different perspectives. This creates a rich, multiperspective knowledge base where convergence and dissonance between viewpoints illuminate complexity.

Notion Database Setup

The system architecture requires three primary Notion databases plus supporting reference databases for characters, locations, and cases. Each database serves a specific function in maintaining the hard/soft epistemological boundary.

Events Database (Hard Layer)

The Events database constitutes the immutable factual foundation of the system. Events are atomic observations that function as an append-only log - they can be created but never edited or deleted.

Event Schema (Required Fields):
Property Name Type Description
Event ID Title Unique identifier in format E-YYYY-MM-DD-NNN
Timestamp Date When the event occurred (datetime precision)
Type Select OBSERVATION, EVIDENCE, STATEMENT, CORRESPONDENCE, NEWS_REPORT, POLICE_REPORT, ANALYSIS, MOVEMENT, TRANSACTION, WEATHER, VISITOR, ABSENCE
Payload Text The factual content - what was observed
Source Text Who observed/reported this event
Verified Checkbox Whether the event has been confirmed
Characters Present Relation Link to Characters database
Location Relation Link to Locations database
Related Case Relation Link to Cases database
Weather Select Clear, Fog, Rain, Snow, Overcast
Ingestion Note Text Meta-commentary about why this event matters
Related to Briefs Relation Auto-populated - which Briefs cite this Event

The Event ID format follows a strict naming convention: E-YYYY-MM-DD-NNN where NNN is a zero-padded sequence number for that day. For example, E-1895-10-10-002 is the second event recorded on October 10, 1895. This creates a chronological, immutable audit trail.

Briefs Database (Soft Layer)

The Briefs database contains interpretive narratives from different outlets. Unlike Events, Briefs are mutable - they can be revised, amended, or marked as provisional as new information emerges.

Brief Schema (Required Fields):
Property Name Type Description
Title Title Descriptive title of the brief
Outlet Select Which narrative voice authored this (Holmes's Case File, Watson's Journal, etc.)
Canon Level Select Provisional, Secondary, Record - indicates epistemic certainty
Status Select Draft, Published, Amended
Published Date Date When this brief was published
Scope Start Date Beginning of time period covered
Scope End Date End of time period covered
Included Events Relation Link to Events cited in this brief
Related Case Relation Link to Cases database
Changelog Text Record of amendments and revisions

Brief pages contain the actual narrative content using Markdown formatting. Each interpretive claim within a Brief must cite the Event ID(s) that support it, creating a traceable chain of evidence from interpretation back to immutable fact.

Supporting Databases

Three additional databases provide relational context:

  • Cases Database: Tracks ongoing investigations (e.g., "The Affair of the Missing Rubies", "The Disappearance of Thomas Henley")
  • Characters Database: Maintains information about people who appear in Events (Sherlock Holmes, Dr. Watson, Lady Brackenstall, etc.)
  • Locations Database: Records places where Events occur (221B Baker Street, Brackenstall House, Limehouse, etc.)

These databases use standard Notion relation properties to create bidirectional links between Events, Briefs, and contextual entities.

Claude Integration via MCP

MCP Setup

The Model Context Protocol (MCP) is an open standard that enables AI assistants to interact with external data sources. Notion provides an official MCP server that gives Claude secure, authenticated access to your Notion workspace.

MCP Setup Steps:
  1. Create Notion Integration: Go to https://www.notion.so/my-integrations and create a new internal integration. Save the integration token.
  2. Grant Access: In your Notion workspace, open each database you want Claude to access, click the "..." menu, select "Connections", and add your integration.
  3. Connect Claude: In Claude (web or desktop), the Notion integration should appear automatically via MCP. Authenticate using OAuth.
  4. Verify Connection: Ask Claude to "fetch" a page from your Notion workspace to confirm access.

The MCP connection is read-write by default, meaning Claude can both retrieve and modify Notion content. This is essential for the Multi-Outlet Narrative System workflow where Claude actively creates Events and Briefs.

Available Notion Tools

Claude's Notion integration via MCP provides several key tools optimized for the Multi-Outlet Narrative System:

Tool Function System Usage
notion-fetch Retrieve page or database content Reading existing Events, Briefs, or database schemas
notion-search Semantic search across workspace Finding related Events, discovering existing Briefs, locating specific cases
notion-create-pages Create new pages in databases Adding new Events (to Events database) or new Briefs (to Briefs database)
notion-update-page Modify page properties or content Amending Briefs, updating Canon Level, adding Changelog entries
notion-create-database Create new databases Initial system setup
notion-update-database Modify database schema Adding new Event types or Outlet options

The notion-create-pages tool is particularly important as it allows batch creation of multiple pages and requires careful attention to the parent parameter, which specifies either a page_id, database_id, or data_source_id depending on where the new page should be created.

Implementation Workflow

Creating Events

The Event creation workflow follows strict protocols to maintain the hard epistemological boundary:

Event Creation Example: 
notion-create-pages({
  "parent": {"data_source_id": "14067e5d-3501-4119-8810-74af6efda068"},
  "pages": [{
    "properties": {
      "Event ID": "E-1895-10-10-002",
      "Type": "MOVEMENT",
      "Timestamp": "1895-10-10T08:45:00.000Z",
      "Source": "Mrs. Hudson",
      "Payload": "Mr. Holmes and Dr. Watson departed together at quarter to nine. Both dressed for fieldwork - Holmes in his pea jacket and cloth cap, Watson in traveling coat with medical bag.",
      "Verified": "__YES__",
      "Weather": "Clear",
      "Characters Present": "[\"[Holmes URL]\", \"[Watson URL]\", \"[Mrs Hudson URL]\"]",
      "Location": "[\"[221B Baker Street URL]\"]",
      "Related Case": "[\"[Henley Case URL]\"]",
      "Ingestion Note": "First outdoor investigation since fog lifted. Watson accompanying suggests Holmes expects potential danger."
    }
  }]
})

Critical requirements for Event creation:

  • Atomic: Each Event describes a single discrete observation
  • Factual: No interpretation in the Payload - only what was observed
  • Sourced: Clear attribution of who made the observation
  • Timestamped: Precise datetime when the Event occurred
  • Typed: Classified by Event Type for filtering and analysis
  • Linked: Connected to relevant Characters, Locations, and Cases
Common Pitfall: Avoid putting interpretation in the Event Payload. For example, "Watson looked worried" is interpretive. Instead: "Watson's hand moved to his coat pocket where his revolver was visible" (factual observation). The interpretation that Watson was worried belongs in a Brief, not an Event.

Writing Briefs

Briefs are narrative interpretations that cite Events as evidence. The workflow involves:

  1. Review Events: Use notion-search to find Events within the time period to be covered
  2. Select Perspective: Choose which Outlet voice to write from (Holmes, Watson, Mrs. Hudson, etc.)
  3. Draft Content: Write interpretation in that Outlet's characteristic style and concerns
  4. Cite Events: Reference specific Event IDs throughout the Brief
  5. Set Canon Level: Mark as Provisional (uncertain), Secondary (supported but not primary), or Record (well-established)
  6. Publish: Create the Brief page using notion-create-pages
Brief Content Structure (Watson's Journal example): 
**Watson's Journal**
**Date:** 10 October 1895, Morning

Holmes asked me a question in his Day 6 analysis: *"In your medical 
experience, what psychological state would make someone most susceptible 
to coercion?"*

The answer is precisely what I observed about Thomas Henley: isolation.

**E-1895-10-08-015, E-1895-10-08-016:** Pritchard's account reveals how 
thoroughly alone Henley was. A man can be surrounded by colleagues yet 
profoundly isolated.

**Medical assessment:** Prolonged isolation creates psychological vulnerability.
The isolated individual:
1. Has no external validation of their judgment
2. Cannot distribute emotional burden across relationships
3. Fears consequences more acutely (no support network)

[... continues with Event citations throughout ...]

Notice how Watson's Brief:

  • Maintains his characteristic voice (medical perspective, empathy, moral concern)
  • Cites specific Events by ID (E-1895-10-08-015, E-1895-10-08-016)
  • Adds interpretation and context that Holmes's analytical Brief omits
  • Proposes conclusions that go beyond the raw factual Events

Cross-Outlet Interaction

The system's power emerges from interaction between outlets through the Patch Note mechanism. Outlets can propose amendments to other outlets' Briefs:

Patch Note Pattern: 
## Patch Note for Holmes's Consideration

Re: Your question about psychological vulnerability.

Agreed. However, the medical evidence suggests Henley may be operating 
under duress or threat. The isolation wasn't accidental - someone chose 
Henley *because* he was isolated.

**Recommendation:** When you meet Mycroft today, ask directly about 
Foreign Office involvement. Subtlety is a luxury we no longer have.

Holmes can then:

  • Accept: Incorporate Watson's medical insight into his next Case File, adding it to the Changelog
  • Amend: Issue a new Brief marked "Amended" with updated conclusions
  • Rebut: Publish a response explaining why his analysis differs

This creates a dynamic, multi-vocal narrative where different forms of expertise (logical deduction, medical observation, domestic detail, street intelligence) contribute to collective understanding.

The Sherlock Holmes Example

The Six Outlets

The reference implementation includes six distinct narrative voices, each representing a different epistemological standpoint:

Outlet Voice Focus Characteristic Concerns
🔍 Holmes's Case File Analytical, spare Logical deduction Evidence chains, provisional hypotheses, amendments when proven wrong
📖 Watson's Journal Warm, medical Human dimension Emotional states, medical observations, moral implications
☕ Mrs. Hudson's Ledger Practical, observant Domestic details Visitor patterns, meals, household rhythms, social class markers
📰 The Evening Standard Sensational, public News narrative Public safety, political pressure, sometimes wrong but corrects errors
👮 Scotland Yard Dispatch Official, procedural Police perspective Evidence chains, jurisdictional concerns, bureaucratic constraints
👦 Baker Street Irregulars Street-smart, informal Intelligence gathering Movement tracking, market gossip, places gentlemen can't access

Each outlet observes the same Events but interprets them through their unique lens. For example, when Lady Brackenstall arrives at 221B Baker Street with bruising on her wrist:

  • Holmes notes it as evidence (defensive injury, 48-72 hours old, relevant to theft timeline)
  • Watson diagnoses it medically (bruise pattern suggests forceful grab by larger hand, indicates domestic violence)
  • Mrs. Hudson recognizes it personally (she herself bore such marks years ago from an abusive husband)

This demonstrates how situated knowledge - the unique perspective each observer brings - enriches collective understanding beyond what any single viewpoint could achieve.

Case Study: The Missing Rubies

The case of "The Affair of the Missing Rubies" demonstrates the full system in action across multiple days of investigation:

Day 1 (October 1, 1895):

  • Event E-1895-10-01-001: Lady Brackenstall arrives at 221B, distressed
  • Event E-1895-10-01-002: She reports three rubies stolen from bedroom safe, £12,000 value
  • Event E-1895-10-01-003: Holmes observes bruising on her wrist during interview
  • Event E-1895-10-01-004: Examination of safe reveals jasmine perfume (Lady B. wears rose scent)

Briefs Published (Day 1):

  • Holmes's Case File: Marks analysis as "Provisional" - notes jasmine anomaly suggests another woman accessed safe, questions Lady B.'s full disclosure
  • Watson's Journal: Observes medical signs of genuine distress (elevated pulse, tremor, dilated pupils), proposes Patch Note that bruising indicates domestic violence, recommends investigating male visitors
  • Mrs. Hudson's Ledger: (Day 2) Notes Lady B.'s genuine fear was visible even from hallway, proposes Patch Note distinguishing hired muscle from someone with personal grievance

Day 2 (October 2):

  • Holmes issues Amendment: Creates new Brief "Notes on Day 2 Observations" with Changelog: "Incorporated Patch Notes from Mrs. Hudson and Watson. Set investigation priorities for Day 3."
  • Investigation expands based on converging interpretations from multiple outlets

By Day 4, the convergence of evidence leads to resolution: Captain Croker confesses to extortion following Lord Brackenstall's death. Holmes's final Brief moves from "Provisional" to "Record" (highest canon level), and includes acknowledgment:

"Watson's medical assessment of Lady B.'s genuine distress proved accurate. Mrs. Hudson's observation about the maid's frightened posture was prescient. The human dimension both outlets provided was essential to understanding the full picture."

This demonstrates how the system enables collective intelligence through structured interaction between different forms of expertise.

Best Practices

Event Creation

  • Keep Events Small: One observation per Event. "Holmes examined the safe" and "Holmes noticed jasmine perfume in safe" should be two Events, not one.
  • No Retroactive Editing: If an Event contains an error, create a new Event correcting it. Never edit the original.
  • Precise Timestamps: Use datetime precision, not just dates. This enables temporal analysis.
  • Complete Metadata: Always fill Characters Present, Location, and Related Case. These relations enable powerful queries later.

Brief Writing

  • Cite Liberally: Reference Event IDs frequently. Readers should be able to trace every claim back to evidence.
  • Mark Uncertainty: Use Canon Level appropriately. If conclusions are uncertain, mark as "Provisional" rather than "Record".
  • Maintain Voice: Each outlet should have consistent tone, concerns, and blind spots. Watson shouldn't sound like Holmes.
  • Use Changelog: When amending a Brief, document what changed and why in the Changelog field.
  • Propose, Don't Command: Patch Notes should suggest, not demand. "Consider investigating..." not "You must investigate..."

System Maintenance

  • Regular Reviews: Use notion-search periodically to find uncited Events or orphaned Briefs
  • Schema Consistency: When adding new Event Types or Outlets, document the addition and ensure all users understand it
  • Backup Strategy: Notion's version history provides some protection, but consider periodic exports for critical narratives
  • Access Control: In multi-user scenarios, carefully manage who can create Events (should be restricted) versus who can create Briefs (can be open)

Claude Workflow Tips

  • Batch Operations: Use notion-create-pages to create multiple Events at once when documenting a scene with many observations
  • Fetch Before Update: Always use notion-fetch to retrieve current state before updating a Brief to avoid overwriting recent changes
  • Search for Context: Before writing a new Brief, search for related Briefs from other outlets to understand what's already been interpreted
  • Verify Relations: When creating Events or Briefs, double-check that relation properties (Characters Present, Location, etc.) use correct page URLs
