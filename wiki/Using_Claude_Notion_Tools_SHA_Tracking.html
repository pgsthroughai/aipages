Introduction

This page documents a working system that combines three powerful technologies:

  • Claude AI - Orchestrates the workflow using natural language
  • Notion - Serves as persistent memory for SHA keys and metadata
  • GitHub - Hosts and publishes the wiki pages

The result is a sustainable wiki system where pages can be created and updated conversationally, without manual Git commands or SHA tracking, while maintaining full version control capabilities across multiple sessions.

Why This System Exists: GitHub's API requires the current SHA (commit hash) to update any file. Without tracking these SHAs, you can only create new files - never update existing ones. Notion provides the searchable, persistent storage that makes this possible.

The Wiki SHA Tracking Database

Purpose & Function

The "Wiki SHA Tracking" Notion database serves as the central registry for all wiki pages in the pgsthroughai/aipages repository. It's not just a list - it's the system that enables continuous wiki development.

Key Functions:

  • SHA Storage: Tracks the current Git commit hash required to update each file
  • Metadata Registry: Maintains file paths, URLs, branches, and update dates
  • Multi-Session Continuity: Enables Claude to resume work across different conversations
  • Audit Trail: Shows the complete history of all wiki pages

Database Structure

Each entry in the database represents one wiki page and contains these properties:

Property Type Purpose Example
Page Name Title Exact filename without .html extension Using_Claude_Notion_Tools_SHA_Tracking
SHA Key Text Current Git commit hash for the file dd44a65b3c1951df7cbcdcff044334881cfe69e1
File Path Text Location in repository wiki/Using_Claude_Notion_Tools_SHA_Tracking.html
Page URL URL Live GitHub Pages URL https://pgsthroughai.github.io/aipages/wiki/...
Branch Text Git branch where file exists feat/initial-landing-page
Last Updated Date Most recent change date 2025-10-01

How Claude Uses the Notion Tool

Claude accesses Notion through the Model Context Protocol (MCP), which provides standardized tools for interacting with the database. Here are the core workflows:

Workflow A: Creating a New Wiki Page Entry

Step 1: Create or update file in GitHub 
github_create_or_update_file(
  repo: "pgsthroughai/aipages",
  path: "wiki/Page_Name.html",
  branch: "feat/initial-landing-page",
  content: "...",
  message: "Create new page"
)
→ Returns: {sha: "abc123...", url: "..."}
Step 2: Immediately store SHA in Notion 
notion-create-pages(
  parent: {
    data_source_id: "f87df9e7-50c9-470a-b5eb-584079dad827"
  },
  pages: [{
    properties: {
      "Page Name": "Page_Name",
      "SHA Key": "abc123...",
      "File Path": "wiki/Page_Name.html",
      "Page URL": "https://pgsthroughai.github.io/aipages/wiki/Page_Name.html",
      "Branch": "feat/initial-landing-page",
      "date:Last Updated:start": "2025-10-01",
      "date:Last Updated:is_datetime": 0
    }
  }]
)
✓ Result: Page is created in GitHub AND tracked in Notion. Future updates are now possible.

Workflow B: Updating an Existing Wiki Page

Step 1: Search for the page in Notion 
notion-search(
  query: "Page_Name",
  query_type: "internal"
)
→ Returns: [{id: "...", title: "Page_Name", ...}]
Step 2: Fetch full details to get current SHA 
notion-fetch(
  id: "page-id-from-search"
)
→ Returns: {properties: {"SHA Key": "current_sha", ...}}
Step 3: Update file in GitHub with current SHA 
github_create_or_update_file(
  repo: "pgsthroughai/aipages",
  path: "wiki/Page_Name.html",
  branch: "feat/initial-landing-page",
  sha: "current_sha",  ← CRITICAL: Must match Notion
  content: "...",
  message: "Update page"
)
→ Returns: {sha: "new_sha_xyz...", ...}
Step 4: Update Notion with new SHA 
notion-update-page(
  page_id: "page-id",
  command: "update_properties",
  properties: {
    "SHA Key": "new_sha_xyz...",
    "date:Last Updated:start": "2025-10-01",
    "date:Last Updated:is_datetime": 0
  }
)
✓ Result: Page is updated in GitHub AND Notion reflects the new SHA for future updates.

Workflow C: Finding Pages Across Sessions

Search by keyword: 
notion-search(
  query: "GitHub workflows",
  query_type: "internal"
)
→ Returns all pages containing those keywords
List all pages in database: 
notion-search(
  page_url: "ce59ed2b-7b69-4ad2-91a0-817cc2d1b2c4",
  query: "",
  query_type: "internal"
)
→ Returns all entries in the SHA tracking database

Integration with GitHub Workflow

The Notion database is part of a larger workflow that combines multiple MCP tools. Here's the complete cycle for creating a comprehensive wiki page:

Phase 1: Research & Planning

  1. Research topic: web_search for current information
  2. Read sources: web_fetch for detailed content
  3. Check existing pages: notion-search to avoid duplication
  4. Review related content: browserless_fetch_a_site_s_html to see published pages

Phase 2: Content Creation

  1. Follow template: Use Wikipedia-style structure from Creating Wikipedia-Style Pages
  2. Include all sections: Introduction, TOC, main content, references, styling
  3. Add internal links: Connect to related pages in the wiki
  4. Prepare for finalization: Include finalization stamp

Phase 3: GitHub Deployment

  1. Upload to repository: github_create_or_update_file
  2. Capture SHA from response: Essential for Notion storage
  3. Verify branch and path: Ensure correct location

Phase 4: Notion SHA Storage

  1. Create tracking entry: notion-create-pages with all metadata
  2. Store SHA immediately: Don't delay this step
  3. Include complete metadata: File path, URL, branch, date
  4. Verify entry created: Confirm with search or fetch

Phase 5: Verification & Linking

  1. Check page is live: browserless_fetch_a_site_s_html or direct browser check
  2. Verify all links work: Test internal and external links
  3. Update hub pages: Add to index or category pages
  4. Update related pages: Add reciprocal links where appropriate

Best Practices

Critical Rules (Never Violate These)

  • ✅ Always search Notion first before updating to get current SHA
  • ✅ Store SHA immediately after every GitHub operation
  • ✅ Use exact page names (case-sensitive, underscores not spaces)
  • ✅ Include all metadata in every Notion entry
  • ❌ Never guess or reuse old SHAs - they become invalid after updates
  • ❌ Never skip Notion storage - you'll lose ability to update later
  • ❌ Never assume SHA is unchanged - always fetch current value

Multi-Session Workflow

Starting a new session:

  1. Review Notion database to see all existing pages
  2. Use notion-search to find pages related to current work
  3. Check existing content before creating similar pages
  4. Update hub/index pages when adding new content

Maintaining continuity:

  • Always fetch current SHA from Notion, never from memory or previous responses
  • Update Last Updated date with every change
  • Keep page names consistent with file names
  • Verify entries after creation/update

Error Prevention

Error Cause Solution
GitHub: "object does not exist" SHA is outdated or incorrect Fetch current SHA from Notion again
Notion: No results found Page name mismatch or doesn't exist Check exact naming, create entry if missing
Notion: Database write fails Wrong data_source_id or parent Verify using f87df9e7-50c9-470a-b5eb-584079dad827
Can't update old page SHA never stored in Notion Find current SHA via git log, store retroactively

Quality Assurance

Before finalizing a page:

  • Verify page is published and accessible
  • Test all internal links to other wiki pages
  • Confirm Notion entry exists with correct SHA
  • Check that Last Updated date is accurate
  • Ensure content follows Wikipedia-style template
  • Add reciprocal links from related pages

Troubleshooting Common Issues

Issue: Cannot Update Existing Page

Symptoms: GitHub API returns "object does not exist" or similar error

Diagnosis:

1. Check if SHA is stored in Notion:
   notion-search(query="Page_Name")
   notion-fetch(id) → Look for SHA Key property

2. If SHA exists, verify it matches GitHub:
   Try update with that SHA

3. If SHA missing or wrong:
   - Cannot update without correct SHA
   - Options: Find via git history or create new version

Issue: Notion Entry Not Found

Symptoms: Search returns no results for a page you know exists

Common causes:

  • Name mismatch (spaces vs underscores, capitalization)
  • Page never had Notion entry created
  • Searching in wrong database or workspace

Solutions:

  • Try variations of the name
  • Search by partial name or keywords from content
  • Create missing entry retroactively with current SHA

Issue: Notion Database Write Fails

Error message references wrong ID or permissions

Solution: Always use these exact values:

parent: {
  data_source_id: "f87df9e7-50c9-470a-b5eb-584079dad827"
}

// NOT the database ID (ce59ed2b7b694ad291a0817cc2d1b2c4)
// Use the collection/data source ID instead

Issue: Link Between Pages Broken

Symptoms: Internal wiki links lead to 404

Causes & fixes:

  • Filename changed: Update all links to new name
  • File moved: Update paths in all referring pages
  • Page deleted: Remove or update links from other pages
  • Typo in link: Verify exact filename including underscores

System Architecture Summary

The Three-Layer System:

1. GitHub (Content Layer)

  • Stores actual wiki page HTML
  • Provides version control
  • Publishes via GitHub Pages
  • Requires SHA for updates

2. Notion (Memory Layer)

  • Stores SHA keys for all pages
  • Maintains metadata and audit trail
  • Enables cross-session continuity
  • Searchable by page name or content

3. Claude (Orchestration Layer)

  • Coordinates between GitHub and Notion
  • Handles natural language instructions
  • Performs research and content creation
  • Manages the complete workflow
